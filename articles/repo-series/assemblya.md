# How AssemBLYA works: a bilingual Docusaurus site for a veterans-led hardware project

AssemBLYA is the public documentation site of a veterans-led engineering project. The project builds a **modular payload delivery platform**: drop systems that mount under a drone. In its own words, every new version should be "simpler, more reliable, easier to manufacture, easier to repair, significantly more affordable."

The repository, [`atherdon/assemblya`](https://github.com/atherdon/assemblya), is where that story is written down. It holds the mission, the roadmap, the product line, competitor teardowns, 3D-print references, procurement notes, and a small marketing front end (pricing, FAQ, timeline, About us), in English and Ukrainian.

This article is part of a series about my repositories. It covers what is in the repo, how the site is built, how content moves from a phone photo to a published page, how CI keeps it honest, and what four months of history taught me. Every number below comes from the repository itself (git history, pull requests, and the scripts), as of mid-November 2026.

## What the site contains

The information architecture lives in `sidebars.js`, an explicit sidebar introduced in PR #23. Before that PR the site used Docusaurus' default autogenerated sidebar, and URLs carried long export paths like `/outsourcing-engineering/assemblya/...`. PR #23 moved everything into four topic folders:

```text
docs/
  getting-started/   intro, overview, mission
  specifications/    roadmap, 3d, systems (houdini, model-222, vampire-style)
  user-guide/        orders, communication
  development/       competitors (steel-hornets, nayavu, nazarium, butterfly-case, vaaamp-drop) + research
```

Each top-level category uses a Docusaurus `generated-index` link with its own slug (`/getting-started`, `/specifications`, …). Readers therefore get a landing page per section without anyone maintaining it.

The content falls into three groups:

1. **Narrative pages.** *Mission* explains why the project exists and sets the production model: bulk supply to units and partners, not retail. *Overview* is a one-screen summary with "at a glance" tables. *Roadmap* lists the planned payload configurations, the platform building blocks (3D-printed parts, drop mechanism, sensors and servos), cost and scale goals (10×, 30×, 50× production capacity), and the near-term workstreams.
2. **Engineering references.** System pages such as *Garry Houdini* (`specifications/systems/houdini`), *Model 222* disassembly photos, 3D model references, and an orders page with servo sourcing notes.
3. **Competitor research.** The largest and most image-heavy section, with teardown galleries of systems other teams field: Steel Hornets models 111 and 222, Nayavu variants, Nazarium, a butterfly-style case, and a long *research* page with 23 images.

Next to the docs, `src/pages/` holds a small React marketing site: `index.tsx` (a homepage redesign in PR #21), `pricing.tsx` (three plans, PR #32), `faq.tsx` (EN/UK Q&A arrays, PR #33), `timeline.tsx` (built from the layout in issue #34, PR #35) and `about.tsx` (a team grid, PR #48). Each page has its own CSS module.

## Architecture

### Docusaurus configuration

`docusaurus.config.js` is short and opinionated:

- `baseUrl: '/assemblya/'`, because the site is served under a project path. That detail matters again in the image checks.
- `onBrokenLinks: 'throw'`. A broken internal link fails the build. That's the strictest setting and it's on purpose.
- `onBrokenMarkdownLinks: 'warn'` and `onBrokenMarkdownImages: 'warn'`. Broken *Markdown* links and images only warn. That's a deliberate compromise for a repo that has always had some unrecoverable images (more on that below), and a separate post-build check makes up for it.
- `i18n: { defaultLocale: 'en', locales: ['en', 'uk'] }` with a navbar locale dropdown.
- `@easyops-cn/docusaurus-search-local` for offline full-text search (PR #11), so there's no Algolia account to manage.
- Font Awesome icons in the navbar and footer (PR #14), plus social and contact links (Instagram, Facebook, LinkedIn, TikTok, support, email).

### Two languages, one tree each

PR #27 added i18n in one go: 209 files and +2,612 lines. The Ukrainian site mirrors the English one:

```text
docs/                                         English source
i18n/uk/
  code.json                                   homepage + React UI strings
  docusaurus-theme-classic/{navbar,footer}.json
  docusaurus-plugin-content-docs/
    current.json                              sidebar category labels
    current/                                  Ukrainian docs tree (same paths as docs/)
```

The rule in `CONTRIBUTING.md` is simple: if a page exists in Ukrainian, edit both trees. Contributors aren't trusted to remember it, so `scripts/check-i18n-sync.mjs` compares the two file lists and prints anything that exists on only one side. It's advisory (exit 0 unless `--strict`) because translation lags are normal. The point is to keep them visible.

`npm run build` builds both locales. The Ukrainian site is served under `/assemblya/uk/`, and `npm run docs:uk` starts the dev server in that locale.

### Static images, not co-located images

Images live in `static/img/<topic>/...` and pages reference them as root-absolute paths (`/img/houdini/...`). Docusaurus serves `static/` at the site root and prefixes the `baseUrl` for Markdown images automatically. For raw JSX `<img>` tags in MDX it doesn't, which is why several pages use `useBaseUrl()` (PRs #92 and #97).

One `static/` tree means the English and Ukrainian pages share the same image files. A recompression or a path fix then lands once, not twice.

### Generated files

CI commits two files to `main`, and nobody should edit them by hand:

- `CHANGELOG.md`, regenerated with `auto-changelog` after every push to `main`;
- `docs/pages-index.md`, an "All pages" inventory produced by `scripts/generate-docs-index.mjs`.

The index generator lists every page's path and front-matter title as plain code spans, not links. The comment in the script explains why: unlisted or out-of-tree docs would otherwise trip `onBrokenLinks: 'throw'`. It's a small decision that keeps a strict build setting compatible with a messy docs tree.

## The content workflow

The repo's history shows two very different ways content arrives.

### Mode 1: straight from the field

Most commits are titled "Add files via upload", "Update readme.md", "111" or "333". That's the GitHub web UI on a phone or laptop: photos uploaded into a folder, a Markdown file edited in the browser, committed directly to `main`. July and August, with 282 commits between them, were almost entirely this mode.

This is the right workflow for the person who knows the hardware. It's also the source of nearly every maintenance problem in the history:

- Files get renamed or moved in the UI, and the Markdown keeps pointing at the old path. On 2026-08-09 and 08-10 the Houdini gallery was reorganized: files renamed from `…-jpg-06-25-2026_11_29_PM.png` to short names, and some moved into `static/img/houdini/butterfly/`. The page kept the old refs.
- Sections that aren't ready are hidden with HTML comments (`<!-- … -->`) instead of being deleted. That's a good habit, but simple scanners can't see the difference.
- Some uploads arrive damaged. The `steel-hornets-cheap-steal` photos in the repo, and the copies in the older `fuck-ecoflow` repo, are UTF-8-mangled: every non-ASCII byte became `EF BF BD`, so none of them decode as JPEG.

### Mode 2: cleanup sprints through draft PRs

The second mode is engineering work in small draft PRs. Some are opened by me, some by coding agents, and some are mirrored from the `LLazyEmail/assemblya` fork, which is where much of the modernization work started. The conventions are written down in `AGENTS.md` and `CONTRIBUTING.md`:

- branch from `main`, keep PRs small and single-purpose, open them as **draft** until CI is green;
- never delete content; annotate or extend it instead;
- edit EN and UK together;
- every commit carries a `Co-authored-by: petroved` trailer.

The July sprint (PRs #2 to #48) turned a raw export into a site. PR #2 made it buildable at all: it installed Docusaurus 3.10.2, removed an npm dependency that doesn't exist (`@docusaurus/module-alias`), fixed `_category_.json` IDs that still pointed at old paths, and disabled the empty blog plugin. Later PRs added deployment, local search, SEO metadata, the homepage, the topic hierarchy, i18n, and the marketing pages.

The November sprint (PRs #82 to #109) was about images and CI, and it's the more interesting story.

## The image saga: LFS, pointers and the build image check

### Step 1: getting out of Git LFS

AssemBLYA notes started on 2026-06-21 as a folder (`docs/01-outsourcing-engineering/AssemBLYA`) in my larger `fuck-ecoflow` docs repo, which stores media in Git LFS. This repo was created three weeks later. Some files arrived here as **LFS pointer files**, the 130-byte text stubs that start with `version https://git-lfs.github.com/spec/v1`. The real objects weren't available: they returned 404 on this repo and on the fork.

On the live site a pointer looks like a broken image. Docusaurus will happily copy a text file named `.jpg`.

The fix ran across PRs #89, #90, #91 and finally #97, "demigrate LFS media". It replaced pointer files with real binaries committed as **normal git blobs**, in batches of at most 15 files per PR so each one stayed reviewable. It also deliberately did *not* merge the fork's PR that would have added LFS `.gitattributes`.

The resulting rule is short and strict: **this repo doesn't use Git LFS**. The CI build checks out without LFS (`lfs: false`), and the build image allowlist header says "Remove an entry only after the real asset is restored (never via Git LFS)."

Why not LFS? Bandwidth and storage quotas, the extra checkout step in every workflow, and the failure mode. A missing LFS object doesn't fail anything. It silently turns into a pointer that ships as an image.

### Step 2: making images smaller

Once the images were real, they were also heavy. PRs #99, #100 and #102 recompressed the competitor galleries. Large PNG photos became JPEG (max width 1600 px, quality about 80, mozjpeg), and the EN and UK pages were updated together.

The first batch alone took 12 assets from about 7.7 MB to about 2.0 MB and the *research* page from 14.79 MB to 9.54 MB. The PRs used the same 15-files-per-PR cap. The originals are still in git history, so nothing was lost.

### Step 3: checking the *built* site, not the Markdown

The repo already had `scripts/check-missing-images.mjs`, which reads Markdown sources and reports `![…](…)` refs that don't resolve on disk. It's useful, but it can't see:

- raw HTML and JSX `<img>` tags in MDX;
- `baseUrl` mistakes, where the file exists but the URL the browser requests doesn't;
- files that exist but aren't images (LFS pointers, two-byte placeholders, mangled JPEGs).

PR #98 added `scripts/check-build-images.mjs` (336 lines) and the **Build image check** workflow. It runs after a real build of both locales and walks every HTML and CSS file in `build/`. For each local `<img src>`, `srcset` candidate and CSS `url(…)` that looks like an image, it checks four things:

1. Resolve the URL against `build/`, respecting `--base-url /assemblya/`.
2. Assert the file exists and is non-empty.
3. Sniff the **magic bytes** (PNG, JPEG, GIF, WebP, ICO, BMP, SVG and so on), not the extension.
4. Reject anything that starts with the LFS pointer header.

Failures are printed as a Markdown table and written to the job summary, and the job exits 1.

Some assets really are unrecoverable, so the check reads `scripts/build-image-allowlist.txt`. The allowlist works like a list of known debts:

```text
# Empty stub PNGs (2-byte CRLF placeholders) under static/img
/img/master-plan.png
...
# TODO(arthur): source files missing everywhere in the repo ...
# cheap-steal: img2-img13 never committed; img1 has a corrupt JPEG header
```

Every entry has a reason, and issue #105 tracks getting the originals back. The check is strict about everything else.

When PR #98 was opened, its own dry run on `main` found **92** non-allowlisted failures. That number is the best argument I have for checking build output: the site had been "green" the whole time.

### Step 4: removing noise from the advisory checks

The newest work (open as of this writing) is about trust in the advisory checks. On `main`, `check:images` reported 36 missing refs. 12 of them were inside HTML comments, sections that were hidden on purpose. PR #114 lists those separately as "hidden" so the real count, 24 refs to the missing cheap-steal photos, stands out.

PR #115 repoints the hidden Houdini gallery to the renamed files. Each mapping is proven with matching git blob hashes, so un-hiding the section later just works.

## CI: thirteen workflows, almost no YAML

Every workflow file in `.github/workflows/` is a short caller of a reusable workflow or composite action from [`LLazyEmail/documentation-actions`](https://github.com/LLazyEmail/documentation-actions) ("DA"), the shared CI library I maintain for my documentation sites. A typical caller is about 20 lines:

```yaml
jobs:
  i18n:
    uses: LLazyEmail/documentation-actions/.github/workflows/reusable-npm-script-check.yml@v1
    with:
      working-directory: .
      cache-dependency-path: package-lock.json
      node-version: '24'
      job-name: Check i18n sync
      run-command: npm run check:i18n
```

On pull requests:

| Workflow | Runs | Effect |
| --- | --- | --- |
| Test deployment | Docusaurus build via DA's `docusaurus-build` action | red on failure |
| Build image check | build, then `check-build-images.mjs` with the allowlist | red on failure |
| Format check | `npm run format:check` (Prettier) | red on failure |
| Typecheck | `npm run typecheck` (`tsc --noEmit`) | red on failure |
| Markdown lint | markdownlint on README, CHANGELOG, AGENTS, CONTRIBUTING, docs, i18n | red on failure |
| Link check | lychee, also weekly on a schedule, opening an issue | red on failure |
| Missing images check | `npm run check:images` | advisory |
| i18n sync check | `npm run check:i18n` | advisory |
| Star request comment | one friendly comment on newly opened PRs | — |

On `main`: **Update changelog**, **Update docs pages index**, **Deploy**, and **Auto-rebase open PRs** (every six hours).

Most PR workflows have `paths:` filters. A docs-only PR doesn't run Typecheck, and a script-only PR doesn't run Link check.

The design decisions behind this:

- **One library, many repos.** The same reusable workflows run this site, `fuck-ecoflow`, and the LLazyEmail sites. A fix in DA is released once and picked up by every caller through the `@v1` tag. That's also why callers pin a major tag and not `@main`: a DA change can't break this repo until it is released.
- **Repo logic stays in npm scripts.** Each check is `npm run something`. DA provides the runner, Node setup and caching, and the repo provides the logic in `scripts/*.mjs`. Contributors run exactly what CI runs.
- **Advisory vs. strict is a per-check decision.** i18n drift and source-level image refs are advisory. Build output, formatting, types and links are strict.

### A real CI failure from this month

Every open Renovate PR (#107, #108, #110 and #111) and the DA v2 bump (#112) failed **Format check** on one file, `docs/pages-index.md`. The cause took two minutes to find once I looked.

The generator writes a compact table separator (`| --- | --- | --- |`), and Prettier wants padded columns. The file is regenerated by CI on every docs push, so formatting it once would be undone by the next push.

The right fix was to treat it like `CHANGELOG.md` and add it to `.prettierignore` (PR #113). It's a one-line change that unblocks five PRs. The lesson is the general one: **generated files need to be excluded from every checker that runs on human-written files.** That means formatting, i18n parity (PR #114 does the same for `check:i18n`) and linting.

### Another one: auto-rebase that never rebased

Auto-rebase runs every six hours and updates PR branches that are behind `main`. The logs showed lines like:

```text
#108: No update required (state: unstable)
#107: No update required (state: unstable)
#106: Failed: Conflicts require opt-in rebase-conflicts mode
```

GitHub reports `mergeable_state: unstable` (failing checks) before it reports `behind`. So a PR that was both behind *and* red was never updated, and it couldn't get green without an update. That deadlock was fixed in DA itself: documentation-actions #137, released in v2.0.1, now compares the branch with its base when the state is `unstable` or `blocked`. It reaches this repo only through the v2 bump (#112), because callers pin a major tag. That's the other half of the shared-library bargain.

## The fork relationship

`LLazyEmail/assemblya` is a fork of `atherdon/assemblya`. Modernization work often lands on the fork first and then comes upstream through "sync" PRs.

That creates its own problems. PR #106 (fork `main` into upstream `main`) conflicted on `CHANGELOG.md`, which both sides regenerate. It was superseded by #109, a merge that kept upstream's generated files. Its net file diff was empty, but it made the fork's commits part of upstream history, so both sides could sync cleanly afterwards.

The lesson: if two repos both generate the same file, every sync conflicts on it. Resolve those conflicts by regenerating, never by hand-merging.

## Design decisions, summarized

1. **Explicit sidebar over autogenerated.** It costs one file to maintain and gives stable URLs, readable labels, and sections with landing pages.
2. **Strict links, lenient Markdown images, strict built images.** The build fails on broken internal links. Broken source images only warn, because some assets are lost. The post-build check fails on any *new* broken image and keeps known losses in an allowlist with reasons.
3. **No Git LFS.** Normal blobs, compressed before commit, at most 15 binary changes per PR.
4. **Generated files are CI-owned**, and excluded from formatting and parity checks.
5. **Hide, don't delete.** Unfinished sections go inside HTML comments, and tools are taught to tell hidden from broken.
6. **Thin workflow callers over a shared library**, pinned to a major version.

## Lessons learned

**A green build can still be a broken site.** Docusaurus treats a 130-byte text file named `.jpg` as a perfectly good asset. Only checking the built HTML and the actual bytes found the 92 broken images.

**Web-UI edits and renames are the main source of drift.** That's not a reason to stop using them, since they're how field knowledge gets in fast. It's a reason to run cheap checks on every push that point at exactly which ref broke.

**Make advisory checks quiet enough to read.** A report with 36 entries, a third of them false, gets ignored. After teaching the scanner about HTML comments and generated files, every remaining line is a real task.

**Prove every repair from history.** For each renamed image, the fix compared git blob hashes instead of guessing from file names. Where nothing could be proven (the mangled cheap-steal photos), the gap stays open in the allowlist and in an issue, and nothing gets faked.

**Small PRs scale better than big ones, even for binaries.** The 15-files-per-PR cap made every image PR reviewable in the GitHub UI and easy to revert on its own.

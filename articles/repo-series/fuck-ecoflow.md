# How fuck-ecoflow works: turning 1,400 phone commits into a documentation site

The name is blunt on purpose. `fuck-ecoflow` started as a notebook about building **portable charging stations** for frontline units. The goal was to find alternatives to expensive commercial power stations (EcoFlow being the best-known brand): self-built units, which the repo calls "white box" (`charging-station/wb-vs-ecoflow`), designed around LiFePO4 cells and parts volunteers can source. 78 pages mention LiFePO4 or BMS boards.

The problem statement in the repo, written from the Pokrovsk direction, explains why. Positions get discovered and shelled, evacuation is hard, heavy equipment is left behind, and "most of it is purchased by volunteers."

Over five months the repository grew into a lot more than charging stations:

- charging-station cases, tasks and component research;
- outsourced engineering projects (including the first home of AssemBLYA, which later became its own repo);
- communication with partners, team pages and status reports;
- 3D-print files;
- maintainer notes on EcoFlow's APIs, BLE and MQTT.

All of it is published as a Docusaurus site.

This article is part of a series about my repositories. It explains how the repo is organized, how a stream of photo uploads becomes pages, why media is the hard part, and what CI does about it. Every number comes from the git history, pull requests and scripts as of mid-November 2026.

## Architecture

### Docusaurus with redirects as a safety net

`docusaurus.config.js` sets `baseUrl: '/fuck-ecoflow/'`, `onBrokenLinks: 'throw'`, and warn-only behavior for broken Markdown links and images. Like the AssemBLYA site, it uses `@easyops-cn/docusaurus-search-local` for offline search.

The interesting part is at the top of the config. Pages move a lot here, so the site uses `@docusaurus/plugin-client-redirects` in two ways:

1. A `manualRedirects` list for individual moves, e.g. `/docs/reports/report-june-2026` → `/docs/reports/status/june-2026`.
2. A generated list for the whole AssemBLYA section. `getAssemblyaRedirects()` walks `docs/01-outsourcing-engineering/AssemBLYA` at build time, computes each page's route, and adds redirects from both historical spellings (`/AssemBLYA/…` and `/AssemBlya/…`) to the normalized lowercase route.

So when PR #46 normalized the AssemBLYA routes, old links kept working without anyone listing them by hand. A later thin-content scan counted 47 redirect stubs, which are old URLs that still resolve.

### Media: Git LFS, with rules

Images and video are the bulk of the repo. `.gitattributes` sends `*.png`, `*.jpg`, `*.jpeg`, `*.gif`, `*.webp`, `*.mp4`, `*.mov` and `*.pdf` to Git LFS. That rule was added in PR #40 ("Step 20: Add media guardrails"), which means everything uploaded during the first three weeks went in as ordinary git blobs.

Three scripts enforce media policy on pull requests. Each one only looks at files a PR *adds, copies or renames*, so it never blocks on historical content:

- `check-media-guardrails.mjs` blocks newly added local videos (`.mp4`, `.mov`), because videos belong on Dropbox, and blocks new images above a size limit;
- `check-naming-conventions.mjs` wants kebab-case path segments and flags UUID-style folder names left behind by exports;
- `optimize-doc-media.mjs` (`npm run optimize:media`, with `--dry-run`) recompresses images with Sharp and deliberately skips video.

One honest detail from the history: on 2026-06-25, a day after the guardrails landed, the size limit was raised to `2 * 1024 * 1024 * 100` bytes (200 MiB) in a web-UI edit. In practice the image size guard has been off since then. That's a reasonable choice when you're uploading straight from a phone in the field, but you should know about it if you rely on the check.

## The June 2026 cleanup: a 20-step plan

By late June the repo had all the problems of a raw export: duplicate pages, unstable file names, UUID folders, large media in the docs tree and a build that didn't pass. Issue #17, "Cursor clean up plan," broke the fix into a **20-step PR plan** in phases:

1. **CI first.** Step 1 (PR #20) added a build workflow before fixing anything, so that every later step had a red/green signal. The PR body says it outright: "`main` already has Docusaurus build blockers. This PR intentionally adds the guardrail first."
2. **Core routes.** Steps 2 to 4 added a homepage, `docs/intro.md` and a charging-station landing page.
3. **Structure.** Step 5 added `_category_.json` metadata and Step 6 a repository organization guide. Steps 8 to 11 normalized slugs, marked obvious duplicates as drafts (not deleted), fixed duplicate routes and renamed a malformed readme.
4. **Media.** Step 14 added optimization tooling, Step 15 optimized images, Step 17 wrote the MP4 manifest, and Step 20 added the LFS rules and guardrails.

Most of the plan merged on 2026-06-24, together with gallery reorganizations (#18, #25, #26, #31, #41, #43, #47 and #49), a move of `docs/images` into `static/img` (#52), the move of loose `abs-dont-look-here` notes into proper sections (#56), and a navigation reorganization (#58).

The plan worked because each step was small, single-purpose and verified by the build. The PR bodies repeat the same three lines: what's in scope, what's *not* touched, and which commands passed.

## The image saga

Media caused every serious incident in this repo. Here they are in order.

### 1. Placeholders from web-UI renames

In June, galleries were renamed in the web UI to tidy names like `dissasembling-01-img7.jpg`. Some of those renames produced **2-byte files containing only `\r\n`**, and every one of them had the identical blob. The page looked fine in Markdown and showed nothing in the browser.

PR #81 (November) found them with a local build: 144 images Docusaurus "can't read," 5 unresolved Markdown images, and 117 missing `<img>` refs reported by the shared build image checker. It restored **139** originals from git history (for example from commit `fd8aab4`), resized them to 1600 px at JPEG quality 78 to match `optimize-doc-media.mjs`, and numbered them by capture time, because the old numbering couldn't be recovered from identical blobs.

The same PR fixed four "double pointer" PNGs (an LFS object that was itself another LFS pointer) and a few wrong relative paths. One photo, `dissasembling-09-img19.jpg`, had no match anywhere in history. Following the "never delete docs" rule, PR #86 didn't delete the reference. It replaced the image with an HTML comment explaining what's missing and how to restore it.

### 2. Deploying pointers instead of images

After #81 the build was correct locally, but the live site still showed **533 broken images across 70 pages**. The deploy workflow checked out the repo *without* LFS objects, so the site was built from 130-byte pointer files. Docusaurus inlined them as `data:image/...;base64,` URIs, and the build passed.

PR #82 set `lfs: true` on the deploy job. Then PR #83 added the shared **build image check** in `mode: fail` with LFS enabled. It builds the site with real images and fails the PR if any built page references an image that's missing, empty, not an image, or an LFS pointer, including pointers Docusaurus has inlined as `data:` URIs. Detecting those took a dedicated release of the shared library. With #81 merged, the check scans 1,474 image refs and finds 0 problems.

### 3. Binaries that bypassed LFS

The newest incident shows up as red runs of **Update changelog** and **Update docs pages index** on `main`:

```text
Encountered 168 files that should have been pointers, but weren't:
...
 ! [rejected]        HEAD -> main (fetch first)
push rejected (attempt 1); rebasing onto origin/main
error: cannot pull with rebase: You have unstaged changes.
```

168 files match the LFS patterns but were committed as plain blobs: the pre-#40 uploads plus some later web uploads. On checkout, git-lfs flags them and git considers the work tree modified.

That's harmless until two commits to `main` race, which happens on every docs merge: the changelog and docs-index bots both commit after the same push. The loser's first push is rejected, the retry runs `git pull --rebase`, and git refuses because of the "unstaged changes."

The fix (PR #92) is `git add --renormalize .`, which converts all 168 files into LFS pointers without changing their content. `git lfs fsck --pointers` is now the check to run.

### 4. A missing-images report nobody could use

`npm run check:images` reported **136** missing image refs on `main`. When I re-resolved each one, 130 pointed at files that exist. The script:

- resolved `/img/...` against the filesystem root instead of `static/`;
- didn't decode `image%201.png`;
- stopped parsing at the first `)` in names like `photo_(1).jpg`;
- counted examples inside inline code;
- scanned the deliberately unpublished `abs-dont-look-here/` folder.

PR #93 fixes all five and lists refs inside HTML comments as "hidden." The count drops to **0**, so the report can finally become a gate.

## Walkthrough: one page from issue to site

The most recent content PR shows the whole flow in miniature. Issue #89 asked for a page about *Lesnik*, with two photos and a video attached to the issue. PR #90 (merged 2026-11-16) did it like this:

1. **Folder and category.** It created `docs/01-outsourcing-engineering/lesnik/` with a `_category_.json`. The sidebar is autogenerated, so that folder *is* the navigation entry. The name is lowercase kebab-case because `check:naming` rejects spaces, parentheses, uppercase and UUID-only folders in new docs paths.
2. **Images through LFS.** The two photos were saved as `images/lesnik-img1.jpg` and `lesnik-img2.jpg` and committed through Git LFS, as `.gitattributes` requires. The naming pattern `<page>-imgN` is the same one the June gallery PRs introduced.
3. **Video by link.** The video isn't in the repo. `check:media` rejects new local `.mp4`/`.mov` files, so the page links the Dropbox copy.
4. **Room for text.** An empty paragraph follows each photo and the video, so descriptions can be added later from the web UI without touching the layout.
5. **Checks.** The naming check, the media check and `npm run build` passed on the PR. The build image check confirmed that the built page references real image bytes.
6. **After merge.** CI regenerated `CHANGELOG.md`, and because a file under `docs/` changed, it also regenerated `docs/pages-index.md`. The deploy job rebuilt the site with LFS objects.

Step 6 is also where incident 3 showed up. On the push for #90, the docs-index bot committed `docs/pages-index.md` first (`b605db5`). The changelog bot's push was rejected, and its retry hit the 168 stray binaries. The content was fine. The plumbing around it wasn't.

## CI: twelve thin callers

All workflows in `.github/workflows/` call reusable workflows from [`LLazyEmail/documentation-actions`](https://github.com/LLazyEmail/documentation-actions), the shared library behind all my documentation sites.

| Workflow | When | What it does |
| --- | --- | --- |
| Build docs | PRs, `main` | Docusaurus build with `lfs: false` |
| Test deployment | PRs to `main` | Docusaurus build |
| Build images | PRs | build **with** LFS and verify every image in the output |
| Media guardrails | PRs touching media | `check:media` on added/renamed files |
| Naming conventions | PRs touching docs | `check:naming` on added/renamed paths |
| Markdown lint | PRs, `main` | markdownlint |
| Link check | PRs, weekly | lychee |
| Star request comment | PR opened | one comment |
| Update changelog | push to `main` | regenerate and commit `CHANGELOG.md` |
| Update docs pages index | docs push to `main` | regenerate and commit `docs/pages-index.md` |
| Deploy | push to `main` | build with LFS and publish |
| Auto-rebase open PRs | every 6 hours | update PR branches behind `main` |

A few design notes:

- **Two builds on purpose.** `build.yml` keeps `lfs: false`. A comment in the file says LFS objects used to 404, and a pointer-only build is fast and still catches broken links and MDX errors. The image-aware build is a separate job that pays the LFS download (about 100 MB per checkout). Today all 520 LFS objects download fine, so whether to switch the main build to LFS is an open choice, not a necessity.
- **Diff-scoped guardrails.** The media and naming checks compare `origin/<base>` with `HEAD`. A repo with 1,400 commits of history can't be made compliant in one go, but it can stop getting worse.
- **Bots commit generated files.** Changelog and docs index are written by CI on `main`, which is exactly why a dirty work tree (incident 3) breaks them.
- **Pinned major versions.** Callers use `@v1` of the shared library (moving to `@v2`), so a library change never surprises the repo without a release.

## Design decisions, summarized

1. **Keep the field workflow.** Web-UI uploads and edits are how knowledge gets in. Tooling has to work around them, not block them.
2. **Guardrails first, cleanup second.** CI landed before the first fix (Step 1 of 20).
3. **LFS for media, enforced and verified.** `.gitattributes` patterns, `git lfs fsck --pointers`, and an image-aware build check.
4. **Videos go to Dropbox**, tracked in a manifest. New local videos are rejected.
5. **Redirects instead of broken links.** Generated redirects for whole sections that were renamed.
6. **Never delete docs.** Duplicates become drafts, missing photos become explanatory comments, and unpublished notes live in `abs-dont-look-here/` outside the site.

## Lessons learned

**A successful build doesn't mean a working site.** Three separate incidents (placeholders, pointer deploys, inlined `data:` URIs) all produced green builds and broken pages. The only reliable check reads the built HTML and the actual image bytes.

**LFS fails silently in both directions.** A missing object becomes a pointer that ships as an image, and a binary that skipped LFS becomes a "modified" file that breaks unrelated automation. Check both: `git lfs fsck --pointers` for the second, a build image check for the first.

**Identical blobs are a fingerprint.** All the broken gallery photos shared one 2-byte blob, and that's how 139 of them were found at once. Blob hashes are also how restorations get proven, not guessed.

**A noisy report is the same as no report.** 136 "missing images" with 130 false positives taught everyone to ignore the check. Fixing the resolver was worth more than fixing any single image.

**Write the plan as PRs.** The 20-step plan turned an overwhelming cleanup into a day of small, reviewable merges, each with a verification line.
